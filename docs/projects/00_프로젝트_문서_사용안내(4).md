# AI 커머스 운영 에이전트 — 프로젝트 문서 사용안내

이 파일은 11개 산출물의 **첫 진입점**이다. 처음부터 모든 문서를 순서대로 정독할 필요는 없다. 오늘 만들 기능을 일정표에서 고른 뒤, 작업에 필요한 문서의 해당 항목만 읽고 코딩하면 된다.

## 1. 프로젝트 한 줄 설명

Cafe24 온라인 주문, Toss POS 오프라인 판매, eCount 재고·입고 자료를 한 운영 데이터로 모아 **재고 불일치, 예약주문 누락, 입고·출시 일정 지연**을 먼저 찾아내고, 근거와 함께 할 일을 제안하는 운영 지원 시스템이다.

21일 안에는 실제 운영 시스템을 AI가 바꾸지 않는다. Production은 읽기 전용이며, 금전·환불·주문취소·가격·실재고 변경을 AI가 자동 실행하지 않는다.

## 2. 가장 먼저 읽을 네 가지

1. [01 프로젝트 종합기획서](01_프로젝트_종합기획서.md)의 `목표와 비목표`로 범위를 확인한다.
2. [06 운영안전 명세서](06_운영안전_명세서.md)의 `최상위 정책`과 `금지 행동`을 확인한다.

## 4. 일정표를 매일 사용하는 방법

### 아침 — 10분

1. `처음읽기` 시트에서 현재 통합 주기와 금지사항을 확인한다.
2. `일일업무`에서 오늘 Day의 큰 목표와 `오늘 완료조건`을 읽는다.
3. `세부작업체크`에서 `일차=오늘`, `트랙=내 트랙`으로 필터링한다.
4. 각 행의 `착수 조건 → 구현 지시 → 구현 위치 → 검증 방법 → 완료 기준 → 완료 증거` 순서로 읽는다.
5. 상태를 `미착수`에서 `진행 중`으로 바꾼다.

### 작업 중

- 다른 트랙이 아직 끝나지 않았으면 기다리지 않는다. `Mock/Fixture/Contract`를 사용한다.
- 설계가 다르게 보여도 먼저 [05 데이터·API 명세서](05_데이터_API_명세서.md)의 계약을 지킨다.
- 실제 사업 데이터는 로컬 출력·스크린샷·Git에 넣지 않는다.
- 금전·환불·주문취소·가격·실재고 변경 경로는 구현·호출하지 않는다.
- 막히면 상태를 `차단`으로 바꾸고 `막힘/다음 조치`에 원인과 필요한 결정을 쓴다.
- 다른 트랙이나 외부 계정 때문에 막혔으면 마지막 열의 `차단 시 대체 방법`으로 계속 진행한다. 대체 경로로 끝낸 작업은 실제 연동 완료로 과장하지 않는다.

### 저녁 — 15분

1. 검증 명령을 실행한다.
2. 테스트 로그, 결과 JSON, 스크린샷, 실험표 등 재현 가능한 경로를 `완료 증거`에 적는다.
3. 완료 기준을 모두 만족할 때만 상태를 `완료`로 바꾼다.
4. 일부만 끝났으면 `검토 대기` 또는 `진행 중`으로 남긴다.
5. `진행현황` 시트에서 오늘과 트랙의 완료율을 확인한다.

## 5. “게이트”가 무엇이었나

이전 문서의 Gate는 새로운 기능명이 아니라 **다음 단계로 넘어가기 전 확인점**을 뜻했다. 개정본에서는 이 단어를 다음 두 표현으로 바꿨다.

- `오늘 완료조건`: 그날 작업이 끝났다고 판단하는 기준
- `통합 확인일`: 세 트랙 결과를 실제로 연결하고 계약·데이터 흐름·오류·안전을 함께 시험하는 날

통합 확인일은 Day 4·8·12·16·20이며 Day 21은 최종 확인이다. 다른 트랙을 기다리는 날이 아니다. 통합 전까지 각 트랙은 계약과 Mock으로 독립 개발하고, 확인일에 현재 결과를 연결한다.

통합 확인일이라고 세 트랙을 하나의 인위적인 E2E로 강제하지 않는다. `현재 구현된 기능 + 확정된 공동 계약 + 실제 연결 가능한 Interface`만 연결한다. 계약이 맞지 않으면 없는 필드·enum·adapter를 임시로 만들지 않고 `PARTIAL/BLOCKED`와 Finding으로 남긴다. Finding은 owner와 재검수 Day를 정해 다음 관련 통합 확인일에 다시 검증한다.

## 6. 코드 작업을 시작할 때의 최소 입력 묶음

AI나 개발자에게 코딩을 맡길 때 아래 다섯 가지를 함께 준다.

1. 일정표의 `작업 ID` 한 개 또는 서로 연속된 작은 묶음
2. 연결된 요구사항 ID
3. [05 데이터·API 명세서](05_데이터_API_명세서.md)의 관련 스키마/API
4. 일정표 행의 구현 위치와 완료 기준
5. [09 테스트·평가계획서](09_테스트_평가계획서.md)의 관련 시험 항목

예: `D01-BE-02를 구현한다. FR-INT-004와 EventEnvelope v0.1을 따르고, contracts/events.py 및 contracts/tests/test_event_envelope.py를 수정한다. pytest 명령이 통과하고 예시 JSON과 스키마 검증 로그를 남겨라.`

이 정도 입력이면 구현 대상, 수정 위치, 계약, 검증이 모두 정해져 있어 구체적인 코드를 작성할 수 있다. 반대로 “Day 1 백엔드 진행”처럼 범위만 주면 작업 해석이 달라질 수 있으므로 사용하지 않는다.

## 8. 외부 API 데이터 연동은 언제, 어떻게 진행하는가

| 일차 | 실제 작업 | 그날 끝났다고 보는 증거 |
|---:|---|---|
| 1~4일차 | 공통 Provider 계약, Mock, Inbox, 중복방지, 계약시험 | 외부 계정 없이 세 Provider Mock이 같은 계약을 통과 |
| 5일차 | Cafe24 공식 지원범위·권한 결정, 실제 Read Adapter, 보호 staging, 제한 smoke | 공식 근거, page/cursor, 건수 대사, PII 0, 외부 쓰기 0, 원본 무변경 |
| 6일차 | Toss POS·eCount의 API/Webhook/파일 중 한 방식 확정, Adapter 또는 Importer, DTO 매핑 | Provider별 선택 방식 1개, 미지원 항목, 필드 매핑표, 중복 입력 효과 1회 |
| 7일차 | 증분 cursor/checkpoint, rate limit, retry, 부분실패 재개, quarantine, 재처리 | 실패 시 cursor 미전진, 429 준수, 무한 재시도 0, 애매한 데이터 원장 미반영 |
| 8일차 | 선택된 실제 Read 또는 보호 파일 Import를 정규화·원장까지 통합 | `LIVE_READ/FILE_IMPORT/CONTRACT_ONLY/UNSUPPORTED` 판정과 Provider별 증거 manifest |

일정표에서는 먼저 `API연동실행표`를 읽고, 이어서 `세부작업체크`의 `D05-BE-01`부터 `D08-BE-05`까지 실행한다. 공식 문서 URL, API 버전, 인증, resource/endpoint 또는 export 메뉴, pagination, rate limit, 조회기간, 확인시각, 담당자를 채우지 못하면 Production 동기화를 시작하지 않는다.

API가 제공되지 않거나 계약 권한이 없을 때도 기능을 삭제하지 않는다. 같은 `ProviderReadPage` 계약을 구현하는 파일 Importer로 전환한다. 필수 상품코드·수량·시각·단위가 없는 경우 값을 추정하지 않고 `UNSUPPORTED` 또는 Mapping/Quarantine 상태로 남긴다.

## 9. 작업 한 행의 완료 판정 규칙

작업은 다음 여섯 조건을 모두 만족해야 `완료`다.

1. `착수 조건`을 충족했다.
2. 지정된 `구현 위치·예상 파일`에 결과가 있다.
3. `검증 명령·방법`이 통과했다.
4. `완료 기준`을 전부 만족했다.
5. `안전 확인`에서 금지 호출·PII·Secret이 0이다.
6. 재실행 가능한 로그·JSON·스크린샷 경로를 `완료 증거`에 적었다.

계정 승인 없이 Fixture로 통과한 Provider 작업은 `CONTRACT_ONLY`이며 `LIVE_READ`로 표시하지 않는다. 이것이 실제 연동 여부를 혼동하지 않는 기준이다.

## 10. 실제 개발 도구와 질문지 역할

이 프로젝트는 사용자가 핵심 코드와 연결 구조를 이해하고 직접 수정하는 개발 프로젝트다. Backend·Frontend에서는 사용자가 해당 Day의 핵심 코드를 확인·수정하고 기본시험을 실행한 뒤 Codex를 리뷰·시험 보강에 사용할 수 있다. AI·ML 트랙은 Chat, Windows CMD, 모델 API, RunPod로 진행하며 Codex를 직접 사용하지 않는다.

| 영역 | 계획·판정 | 상시 실행 도구 | Codex 사용 규칙 | 결과 전달 |
|---|---|---|---|---|
| AI·ML 실험·모델학습 | AI·ML Chat 질문지 | 로컬 터미널/API/RunPod GPU | Codex 사용 금지. 파일 존재 확인 → 내용 작성·수정 → 의존성 확인 → 실행 순서를 지킨다. | Metric·비용·오류 분석·Artifact 경로 |
| 백엔드·데이터 | 백엔드 Chat 질문지 | VS Code 터미널 + 프로젝트 서비스·DB | 사용자의 구조 확인·핵심 수정·기본시험 후 코드 리뷰, 경계·안전 시험, 반복 작업, 관련 범위 회귀에만 사용한다. | 사용자 수정과 Codex 수정, 시험·API 증거를 분리 |
| 프론트엔드·제품 | 프론트 Chat 질문지 | Figma AI·브라우저·Mock | 사용자의 Component·State·CSS·기본시험·브라우저 확인 후 접근성·경계 상태·계약·회귀 보강에만 사용한다. | Figma 인계·사용자 수동검수·시험·빌드 증거 |
| 전체 일정 | Work 일정관리 질문지 | 이 일정표 | 세 트랙의 최종 검수 보고만 하루 단위로 취합하며 다음 Day를 자동 시작하지 않는다. | 일별 판정·차단·전달사항·누적 현황 |

Codex CLI 사용은 필수가 아니다. 기본 방식은 VS Code에서 프로젝트 루트를 열고 공식 Codex IDE 확장을 사용하는 것이다. Codex 앱을 사용할 때도 같은 프로젝트 루트를 선택해야 동일 파일을 수정한다. 한 저장소에서 두 Codex 작업을 동시에 실행하지 않는다.

```text
│  ├─ tests\                   Vitest 단위·컴포넌트 시험
│  └─ e2e\                     Playwright 브라우저 시험
├─ contracts\                  트랙 공통 Schema·계약과 계약 시험
├─ artifacts\                  실험·통합 실행 증거
└─ docs\                       프로젝트·실험·배포 문서
```

AI 실험용 Agent·LangGraph 코드는 `ai/agents/`와 `ai/experiments/langgraph/`, 실제 운영 LangGraph는 `backend/app/agent/`, Figma 인계는 `frontend/design/figma/`에 둔다. 과거 `apps/api`, `apps/worker`, `apps/web`, `packages/contracts` 경로는 사용하지 않는다.

Frontend는 현재 React/Vite 구조를 사용한다. 향후 일정의 Page 구현 위치는 `frontend/src/app/pages/*Page.tsx`를 기준으로 하며 Next.js식 `app/**/page.tsx` 또는 동적 폴더를 새로 만들지 않는다. 상세 화면은 기존 Route의 Page와 `frontend/src/features/` 아래 Panel/Drawer 컴포넌트로 확장한다.

### 일일 사용자 주도 개발 순서

1. 트랙 질문지가 공식 일정표에서 현재 Day 작업 ID와 완료 조건을 설명한다.
2. 사용자가 관련 파일과 입력 → 처리 → 출력 연결 구조를 확인한다.
3. 사용자가 핵심 코드를 직접 수정하고 기본 단위시험을 작성·실행한다.
4. 사용자가 API 또는 브라우저에서 실제 동작을 확인한다.
5. Backend·Frontend에서만 Codex가 변경 코드 리뷰, 경계·안전 시험 보강, 반복 작업, 계약 차이, 관련 범위 회귀를 수행한다.
6. 사용자가 Codex diff를 확인하고 최종 시험을 실행한다.
7. 트랙 질문지가 사용자 수정과 Codex 수정을 분리한 최종 진행보고를 작성한다.
8. Work 일정관리 질문지가 세 트랙의 최종 보고를 취합해 현재 Day만 판정한다.

일반 Day에도 Backend·Frontend에서 Codex를 사용할 수 있지만, 해당 Day 전체 대리 구현, 사용자 확인 없는 대규모 생성, 미래 Day 선행, 프론트 전체 재작성, 관련 없는 파일 수정은 금지한다.

AI 질문지는 아직 생성되지 않은 Python 모듈이나 테스트 파일을 있다고 가정해 실행시키지 않는다. 예를 들어 `python -m ai.evaluation.validate_schema ...`는 `ai/evaluation/validate_schema.py`, 스키마, Fixture가 실제 생성된 뒤에만 실행한다. 파일이 없으면 해당 작업은 `미완료`이며, 오류 실행 자체를 완료 증거로 사용하지 않는다.

### 백엔드 최초 환경설정과 책임

`D01-BE-01`의 다음 항목은 사용자가 구조와 결과를 확인하며 진행한다. 반복 설정이나 오류 추적은 사용자 기본 확인 뒤 Codex가 보조할 수 있다.

1. 저장소·기존 파일·Git 상태 확인
2. `.venv` 생성과 활성화 방법 기록
3. `pyproject.toml` 또는 lockfile 기준 개발 의존성 설치
4. Node가 필요한 경우 프로젝트 로컬 의존성 설치
5. `.env.example` 생성, 실제 Secret은 `.env`에만 두고 Git 제외
6. DB·Redis 등은 Docker Compose 우선 구성
7. lint·smoke test 실행

Codex는 시스템 전역 Python 패키지를 설치하지 않는다. 관리자 권한, Docker Desktop 설치, 실제 API Credential 입력처럼 사용자 권한이 필요한 작업만 사용자 확인을 받는다.

## 11. Figma AI와 실제 프론트 코드의 경계

Figma AI는 1일차 `D01-FE-01`에서 디자인 시스템과 7개 핵심 화면을 한 번에 생성한다. 결과는 일정표의 `Figma인계표`와 `frontend/design/figma/handoff.md`로 고정한다.

Figma 결과가 담당하는 것:

- 화면 구조와 시각 계층
- 색상·타이포·간격·상태 표현
- 공통 컴포넌트와 화면 Variant
- Loading/Empty/Stale/Denied 등 상태 디자인

사용자와 Codex가 나누어 담당하는 것:

- 사용자: 기존 Route·Page·Component·Type·Mock·Fixture·CSS·Test 연결 확인
- 사용자: 핵심 Component·State·상호작용·CSS 직접 수정과 기본시험 작성
- 사용자: 브라우저 수동 확인과 Codex diff 확인
- Codex: 사용자가 변경한 코드 리뷰와 접근성·경계 상태 시험 보강
- Codex: Type/Contract 차이, 반복 Fixture·시험, 관련 범위 build/regression
- 공통: Production Read-Only와 금지 요청 검증

프론트 질문지는 Figma 검수·인계를 기준으로 기존 코드 구조를 먼저 설명하고, 현재 공식 Day 범위의 사용자 직접 구현과 시험을 작은 단위로 안내한다. 버튼·Drawer·Modal은 해당 Day 범위일 때만 연결하며 전체 화면을 다시 작성하지 않는다.

Figma가 임의로 만든 데이터 필드는 코드 계약으로 사용하지 않는다. 데이터 필드는 항상 `05_데이터_API_명세서.md`가 기준이다.
