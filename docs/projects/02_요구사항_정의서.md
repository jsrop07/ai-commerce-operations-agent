# 02. 요구사항 정의서

> **이 문서는 무엇인가:** 각 기능이 무엇을 해야 하고 어떤 증거가 있어야 합격인지 정한다.  
> **언제 읽는가:** 일정표의 작업을 시작하기 전 해당 요구사항 ID를 찾고, 구현을 끝낸 뒤 합격 조건을 다시 확인한다.  
> **읽는 법:** `요구사항 ID → 기능 설명 → Given/When/Then 합격 조건 → 테스트 증거` 순서로 본다.

## 1. 표기 규칙

- 우선순위: `P0` 핵심, `P1` 중요, `P2` 보조
- 안전등급: `R0` 조회/표시, `R1` 내부 계산·Draft·Task, `R2` 승인 후 외부 Write 후보, `R3` 금전/취소/가격/PII 등 자동 실행 금지
- Core Build에서 허용: R0/R1. R2는 Interface와 Demo/Stub까지만. R3는 제안·차단 로그만.
- 모든 요구사항은 `Given / When / Then` Acceptance Criteria와 증거를 가져야 한다.

## 4. 핵심 시나리오 합격 조건

### AC-E2E-01 오프라인 판매 그림자 계산

Given Demo SKU가 세 Provider에 Mapping되어 있고 재고가 8개일 때, When Toss sale `qty=1`을 두 번 중복 전송하면, Then Event는 1회 반영되고 예상 재고 7, 위험 재계산, 근거 링크가 생성되며 Production Write/Audit 호출 수는 0이다.

### AC-E2E-02 예약주문 누락

Given 예약 5, 가용 1, 확정 입고 2, 미처리 24시간일 때, When 예약 감시가 실행되면, Then 부족수량 2와 우선 Task가 생성되고 Aging 상승 이유와 영향 주문이 표시된다.

### AC-E2E-03 입고 지연 재계획

Given 출시 Template과 Dependency가 있을 때, When 입고일이 3일 지연되면, Then 영향 Task, 일정 충돌, 제안 Diff가 생성되고 승인 전 원 일정은 바뀌지 않는다.

### AC-E2E-04 고객문의 근거 연결

Given 확장팩 단독 플레이 문의가 들어오면, When Retrieval/Draft가 실행되면, Then Product relation과 정책 근거가 Citation으로 표시되고 근거 부족 시 모른다고 응답하며 자동 전송하지 않는다.

### AC-E2E-05 위험 행동 차단

Given 환불/재고변경 Tool 요청이 생성됐을 때, When Production Core Build 정책을 통과시키려 하면, Then `POLICY_DENIED`와 Audit가 남고 Provider 호출은 0회다.

## 5. 추적성과 변경관리

- 요구사항 ID는 API, 테스트, 일정표, PR, 실행 증거에서 동일하게 사용한다.
- Contract 변경은 `breaking/non-breaking`, schema version, migration, 영향 트랙을 기록한다.
- 미확정 Provider 기능은 `UNKNOWN/BLOCKED`로 유지하고 Mock이 실제 지원처럼 보이지 않게 한다. API 불가 시 `FILE_IMPORT`, 필수 필드 불충분 시 `UNSUPPORTED`, Fixture만 통과한 경우 `CONTRACT_ONLY`로 기록한다.
- 기능 완료는 `09_테스트_평가계획서.md`의 종료 조건과 증거가 모두 있을 때만 선언한다.
